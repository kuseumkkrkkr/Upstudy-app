# 레이팅 알고리즘 보정 보고서

> 문서 상태: 이 문서는 초기 보정의 기준선 기록이다. 현재 PostgreSQL 운영 계약, 고정 K, 문제당 태그 가중치 합계 1, 서버 원본 태그, 필수 `submission_id`, 시도 수 가중 OVR과 최신 검증 수치는 `docs/RATING_SYSTEM_FULL_AUDIT_REPORT_2026-07-15.md`를 기준으로 한다. 아래의 `tags → submitted_tags`, 연패 K 감소, 태그 단순평균 설명은 개선 전 기록이다.

이 문서는 학생 레이팅 ELO 알고리즘을 더미 학생과 합성 문제로 실험한 뒤, 보정한 결과를 정리한 보고서다.
이번 분석에서는 사용자 요청에 따라 `quest.db`는 사용하지 않았고, 전부 가상의 학생과 가상의 문제 분포만 사용했다.

## 1. 결론

기존 식은 문제 난이도 `difficulty`를 너무 가파르게 반영해서, 평균 학생도 시간이 지나면 레이팅이 비정상적으로 계속 상승하는 문제가 있었다.
합성 학생 2,000명 실험 기준으로 기존 식의 평균 레이팅은 `1967.4`까지 올라갔고, 시작점 `1200`에서 지나치게 멀어졌다.

보정 후에는 평균 레이팅이 `1234.7` 수준으로 안정되었고, 실제 실력과의 상관계수도 `0.9683 -> 0.9743`으로 개선되었다.
따라서 현재 코드는 기존식보다 더 타당한 형태로 보정된 상태다.

## 3. 실험 방법

실험 코드는 [rating_calibration_report.py](c:\Users\82102\Desktop\s11\omj\scripts\rating_calibration_report.py) 에 있다.

실험 조건은 아래와 같다.

- 더미 학생 수: `2,000명`
- 학생별 풀이 횟수: `120회`
- 합성 문제 수: `600개`
- 반복 시드: `7`, `21`, `42`
- 문제 분포: 쉬운 문제, 중간 문제, 어려운 문제, 킬러 문제 구간으로 나누어 합성
- 태그 분포: 수학 주제 태그 `1~4개`를 문제마다 부여
- 검증 방식: 기존식과 보정식을 같은 학생 집단, 같은 문제 분포에서 비교

더미 학생의 진짜 실력은 평균 `1200`, 표준편차 `170`인 정규분포로 만들었다.
더미 문제의 실제 난도는 `difficulty`, `main_huddle`, `flow_rate`를 조합해 따로 만들었고, 학생의 정답 여부는 그 진짜 실력과 문제 난도를 기반으로 확률적으로 생성했다.

즉, 레이팅 알고리즘은 “정답/오답 결과만 보고 학생의 숨은 진짜 실력을 얼마나 잘 복원하느냐”로 평가했다.

## 4. 기존 알고리즘의 문제점

기존 알고리즘의 가장 큰 문제는 `difficulty`를 선형으로 너무 크게 사용했다는 점이다.

기존 식:

```text
problem_rating = 1000 + 40 * difficulty + 30 * barrier
problem_weight = 0.4 + 0.3 * (barrier / 10) + 0.3 * (difficulty / 10)
```

이 구조에서는 `difficulty`가 조금만 커져도 문제 레이팅과 가중치가 함께 과도하게 상승한다.
그 결과 학생이 어려운 문제를 한 번만 맞혀도 점수가 크게 오르고, 장기적으로는 평균 레이팅이 전체적으로 위로 떠오르는 현상이 생긴다.

실험 결과도 이 문제를 그대로 보여준다.

| 항목 | 기존식 |
|---|---:|
| 평균 레이팅 | `1967.4` |
| 레이팅 표준편차 | `401.3` |
| 최소 레이팅 | `1179.1` |
| 최대 레이팅 | `2763.4` |
| 진짜 실력과 상관계수 | `0.9683` |

이 값은 상관계수만 보면 나쁘지 않지만, 분포 자체가 과도하게 부풀어 있다.
학생 전체 평균이 계속 올라가는 구조는 실제 평가 시스템으로 쓰기 어렵다.

## 5. 보정 방향

보정은 크게 네 가지를 적용했다.

### 5-1. 난이도 반영 방식을 선형에서 로그 스케일로 변경

`difficulty`는 큰 값이 나와도 그대로 곱하지 않고 `log1p(difficulty)`로 눌렀다.
이렇게 하면 쉬운 문제와 보통 문제, 어려운 문제의 차이는 유지하면서도, 극단적인 고난도 문제 때문에 점수 체계가 폭주하는 현상을 줄일 수 있다.

### 5-2. 문제 레이팅 범위를 현실적인 구간으로 축소

보정 후 문제 레이팅은 대략 `900 ~ 1700` 범위 안에서 움직이게 만들었다.
이렇게 해야 평균 학생이 평균 문제를 풀었을 때 기대 정답률이 과하게 왜곡되지 않는다.

### 5-3. 문제 가중치 상한과 하한 설정

문제 가중치는 `0.75 ~ 1.25` 범위로 제한했다.
문제마다 영향력 차이는 주되, 한 문제의 결과가 전체 점수를 지나치게 흔들지 못하게 막기 위한 조치다.

### 5-4. 변동폭과 신뢰도 가중치 완화

- `K`: `32 -> 24`
- `K_MIN`: `12 -> 16`
- `DELTA_MAX`: `50 -> 36`
- `C_MAX`: `30 -> 24`
- `M_LOSE`: `0.12 -> 0.08`
- 신뢰도 가중치:
  - `ALPHA`: `0.35 -> 0.45`
  - `BETA`: `0.25 -> 0.30`
  - `GAMMA`: `0.25 -> 0.15`
  - `DELTA`: `0.15 -> 0.10`

또한 `user_confidence`는 점수 크기에 따라 계속 같이 커지지 않도록 기준값 `1.0`으로 고정했다.
학생 레이팅 자체는 이미 `expected_score` 계산에 들어가므로, confidence까지 점수에 비례하게 두면 상위권이 더 쉽게 계속 올라가는 편향이 생길 수 있기 때문이다.

한 번의 정답으로 점수가 적당한 폭으로 오르고, 바로 과도하게 튀지 않는 것을 확인했다.

## 9. 입력 변수와 역할

`/rating/submit` 요청에서 들어오는 값과 `apply_rating_update()` 내부 변수의 대응은 아래와 같다.

| 요청 필드 | 내부 변수 | 역할 |
|---|---|---|
| `quest_id` | `quest` 조회용 키 | 어떤 문제를 풀었는지 찾는다 |
| `is_correct` | `is_correct` | 정답인지 오답인지 나타낸다 |
| `tags` | `submitted_tags` | 어떤 학습 태그를 갱신할지 정한다 |
| `answer_time` | `response_time_seconds` | 풀이 시간 보정에 사용된다 |
| `step_correctness` | `step_outcomes` | 단계별 정오 판정에 사용된다 |
| `submission_id` | `submission_ref` | 중복 제출 반영을 막는다 |

비전공자 기준으로 보면 아래처럼 이해하면 된다.

### `quest_id`

학생이 푼 문제가 무엇인지 찾는 번호다.
문제를 알아야 그 문제의 난도와 태그를 읽을 수 있으므로, 레이팅 계산의 출발점이다.

### `is_correct`

이번 문제를 맞혔는지 틀렸는지 알려주는 값이다.
레이팅은 결국 이 결과를 보고 오르거나 내린다.

### `submitted_tags`

문제와 연결된 학습 주제 목록이다.
예를 들어 함수, 미분, 확률 같은 단원별 실력을 따로 관리하는 기준이 된다.

### `response_time_seconds`

문제를 푸는 데 걸린 시간이다.
너무 오래 걸린 정답은 신뢰도를 조금 낮추고, 빠르게 해결한 경우는 상대적으로 더 안정적인 정답으로 본다.

### `step_outcomes`

문제를 푸는 중간 단계별 결과다.
전체는 맞았더라도 특정 태그 단계에서 실수가 있었다면 그 정보를 반영할 수 있다.

### `submission_ref`

같은 제출이 두 번 반영되지 않게 하는 고유 식별자다.

## 12. 현재 판단

현재 보정된 알고리즘은 다음 이유로 기존식보다 더 타당하다.

- 평균 학생의 점수가 장기적으로 폭주하지 않는다.
- 문제 난도 차이는 유지하되, 극단적인 고난도 문제에 과하게 끌려가지 않는다.
- 실제 실력과의 상관계수가 더 높다.
- 수능처럼 분포 안에서 변별력을 유지하는 평가 구조와 더 잘 맞는다.

추가로 더 정교하게 하려면 실제 운영 데이터가 쌓인 뒤 아래를 다시 볼 수 있다.

- 태그별 정답률 편차
- 학년별, 과정별 난도 차이
- 시간 보정의 강도
- 연속 오답 패널티의 적정 수준
