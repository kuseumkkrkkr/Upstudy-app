# 레벨테스트 전용 정적 DB 구축 보고서

작성일: 2026-07-14
대상 프로젝트: Upstudy App / OMJ 수학 문제 시스템
상태: 구축 및 운영 DB 반영 완료

## 1. 요약

레벨테스트가 일반 문제은행이나 실시간 문제 생성기에 의존하지 않도록 전용 정적 SQLite DB를 구축했다. 앱의 50문항 풀이 흐름과 현재 레이팅 알고리즘을 기준으로 직접 저작·검수한 문제를 선별하고, 고정 레이팅을 부여해 다섯 개 시험지로 구성했다.

최종 결과는 다음과 같다.

| 항목 | 결과 |
|---|---:|
| 전용 고유 문제 | 98개 |
| 고정 시험지 | 5개 |
| 시험지별 문항 | 50개 |
| 전체 시험지 슬롯 | 250개 |
| 시험지 내부 중복 | 0개 |
| 문제 레이팅 범위 | 1000~1675 |
| 정적 DB 무결성 | `ok` |
| 정적 DB 외래키 오류 | 0건 |
| Python 회귀 테스트 | 21개 통과 |
| Flutter 정적 분석 | 통과 |

레벨테스트 문제는 이제 `omj/data/level_test_static.db`에서만 공급된다. 일반 `quests.db`에는 레벨테스트 문제나 시험지 원본을 저장하지 않고, 사용자 세션·답안·최종 레이팅 같은 운영 데이터만 기록한다.

## 2. 구축 목적

이번 작업의 요구사항은 다음 네 가지였다.

1. 앱의 실제 50문항 레벨테스트 흐름에 적합한 문제를 직접 넣는다.
2. 현재 레이팅 알고리즘이 학생 실력을 안정적으로 복원할 수 있도록 문제 레이팅을 보정한다.
3. 레벨테스트 문제를 일반 문제은행과 물리적으로 분리한 정적 DB에서만 조회한다.
4. 2,000명 이상의 동시 사용 환경에서 반복적인 SQLite 조회와 실시간 문제 생성 비용을 발생시키지 않는다.

## 3. 기존 구조의 문제점

기존 레벨테스트는 다음과 같은 구조였다.

- 일반 `quests.db`에서 재사용 가능한 문제를 검색했다.
- 적합한 문제가 없으면 일반 문제 생성기를 호출했다.
- 동적으로 만든 템플릿과 250개 슬롯을 다시 운영 DB에 저장했다.
- 문제 제목의 실제 교과와 관계없이 슬롯의 `subject_key`가 순환 배정될 수 있었다.
- 채점 시 문제 ID마다 일반 문제은행을 반복 조회했다.

이 구조는 초기 생성 비용, 문제 품질 변동, 일반 문제은행 정리 시 참조 단절, 높은 동시접속 환경의 DB 요청 증가 가능성이 있었다.

## 4. 최종 아키텍처

현재 데이터 흐름은 다음과 같다.

```text
서버 시작
  └─ level_test_static.db 무결성·버전·JSON 검증
       └─ 문제 98개 + 시험지 슬롯 250개를 메모리에 1회 적재

레벨테스트 시작
  ├─ quests.db: 최근 사용자 폼 및 전체 배정 횟수 조회
  ├─ 메모리 정적 스냅샷: 50개 슬롯·문제 payload 조회
  └─ quests.db: 사용자 세션 1건 저장

문항 답안 제출
  ├─ 메모리 정적 스냅샷: 배정된 문항 ID·태그 검증
  └─ quests.db: 답안 upsert

최종 제출
  ├─ 메모리 정적 스냅샷: 50문항 보정 레이팅 일괄 조회
  └─ quests.db: 사용자 전체·태그 레이팅을 한 트랜잭션으로 반영
```

레벨테스트 문항 조회 과정에는 일반 문제은행 검색이나 AI 문제 생성 폴백이 없다. 정적 DB가 누락되거나 손상된 경우 임의 문제를 생성하지 않고 서버 준비 단계가 실패하도록 구성했다.

## 5. 정적 DB 구성

정적 DB 경로는 다음과 같다.

```text
omj/data/level_test_static.db
```

환경변수 `LEVEL_TEST_STATIC_DB_PATH`가 설정된 경우에만 해당 경로로 대체한다. 미설정 또는 빈 값이면 위 기본 경로를 사용한다.

### 5.1 테이블

| 테이블 | 역할 |
|---|---|
| `metadata` | 스키마 버전, 시험지 버전, 인코딩 정보 |
| `problem` | 문제 payload, 교과, 난이도, 고정 레이팅, SHA-256 |
| `template` | 다섯 개 고정 시험지 폼 |
| `template_item` | 시험지별 1~50번 슬롯과 문제 연결 |

정적 문제 ID는 모두 다음 전용 namespace를 사용한다.

```text
level-test-static/v1/...
```

일반 `quests.db`에서 이 접두사를 가진 문제 수는 0개다.

### 5.2 읽기 전용 정책

런타임 연결에는 다음 두 제한을 동시에 적용한다.

```text
SQLite URI mode=ro
PRAGMA query_only=ON
```

운영 중 정적 문제·시험지·슬롯을 수정하는 함수는 제공하지 않는다. 수정은 빌드 스크립트로 새 DB를 완성한 뒤 파일 전체를 원자 교체하는 방식으로만 가능하다.

## 6. 문항 설계

### 6.1 문제 출처

문항은 기존에 직접 저작하고 학생용 문제 계약을 통과한 초기·추가 문제 카탈로그에서 선별했다. 교과 균형 감사 중 공통수학Ⅰ 고난도 슬롯에 합성함수 문항이 잘못 분류된 점을 발견해, 인수정리·미정계수법 기반의 삼차다항식 문항을 전용으로 추가 저작했다.

모든 문항은 다음 조건을 충족한다.

- 앱이 인식하는 `header`, `info`, `data`, `solves` 구조
- UTF-8 한글 문제·해설
- 난이도별 풀이 단계와 분기 수 계약
- 앱의 허용 해시태그 사전
- 고유 문제 ID와 고유 `codebase_id + seed`
- 학생 화면 콘텐츠 검수 계약

### 6.2 시험지별 난이도

각 시험지는 아래와 같이 50문항으로 구성된다.

| 난이도 티어 | 문항 수 | 비율 |
|---:|---:|---:|
| 2 | 10 | 20% |
| 3 | 20 | 40% |
| 4 | 15 | 30% |
| 5 | 5 | 10% |
| 합계 | 50 | 100% |

### 6.3 단계별 구성

| 단계 | 문항 수 | 난이도 구성 | 목적 |
|---:|---:|---|---|
| 1단계 | 20 | 티어 2: 10개, 티어 3: 10개 | 기반 개념과 중간 수준 진입 능력 확인 |
| 2단계 | 20 | 티어 3: 10개, 티어 4: 10개 | 중상 난도 추론과 복합 개념 확인 |
| 3단계 | 10 | 티어 4: 5개, 티어 5: 5개 | 상위권 변별과 고난도 문제 해결력 확인 |

### 6.4 교과 구성

각 시험지는 실제 문제 내용과 태그를 기준으로 다음 교과 분포를 가진다.

| 교과 | 문항 수 |
|---|---:|
| 공통수학Ⅰ | 12 |
| 공통수학Ⅱ | 13 |
| 대수 | 12 |
| 미적분Ⅰ | 13 |
| 합계 | 50 |

같은 교과가 길게 연속되지 않도록 단계·난이도 그룹 안에서 라운드로빈으로 배치한다.

## 7. 레이팅 보정

기존 레이팅 알고리즘은 문제 난이도와 풀이 장벽을 이용해 문제 레이팅을 계산하고, 학생의 50개 정오 결과에 대해 최대우도 추정을 수행한다. 정적 레벨테스트에서는 문제별 `placement_rating`을 명시해 일반 문제 난도 휴리스틱보다 우선 사용한다.

### 7.1 티어별 보정 구간

| 티어 | 고정 레이팅 후보 |
|---:|---|
| 2 | 1000, 1025, 1050, 1075, 1100 |
| 3 | 1150, 1175, 1200, 1225, 1250 |
| 4 | 1325, 1360, 1400, 1440, 1475 |
| 5 | 1525, 1560, 1600, 1640, 1675 |

문제 ID의 안정적인 SHA-256 해시를 사용해 티어 내부의 다섯 레이팅 지점에 결정적으로 분산한다. 같은 DB를 다시 빌드해도 문제 레이팅과 시험지 구성이 변하지 않는다.

### 7.2 합성 학생 시뮬레이션

각 실제 실력값에서 100명의 합성 학생이 레이팅 기대 정답률에 따라 50문항을 풀도록 시뮬레이션했다.

| 실제 실력 | 평균 추정 레이팅 | 평균 절대오차 | 표준편차 |
|---:|---:|---:|---:|
| 900 | 900.6 | 58.0 | 69.2 |
| 1000 | 993.9 | 54.5 | 67.9 |
| 1100 | 1092.7 | 48.8 | 63.6 |
| 1200 | 1190.5 | 41.8 | 54.0 |
| 1300 | 1295.8 | 46.2 | 60.0 |
| 1400 | 1406.2 | 48.4 | 59.9 |
| 1500 | 1522.8 | 53.4 | 67.0 |
| 1600 | 1591.8 | 49.5 | 60.0 |
| 1700 | 1713.5 | 65.5 | 83.9 |

900~1700 구간에서 평균 추정값이 실제 실력에 가깝게 정렬됐으며, 평균 절대오차는 약 42~66점이었다.

## 8. 보안 및 데이터 신뢰성

답안 API는 클라이언트가 제출한 문제 ID와 태그를 그대로 신뢰하지 않는다.

1. 세션에 배정된 정적 시험지 ID를 조회한다.
2. 해당 `item_index`에 배정된 정적 문제 ID와 제출 ID를 비교한다.
3. 불일치하면 HTTP 400으로 저장을 거부한다.
4. 레이팅에는 클라이언트 태그가 아니라 정적 문제에 저장된 검수 태그만 사용한다.

이를 통해 다른 문제 ID 대입, 쉬운 문제로 교체, 임의 태그를 통한 교과 레이팅 조작을 차단한다.

## 9. 동시접속 대응

정적 DB는 서버 시작 시 다음 데이터를 한 번만 읽는다.

- 문제 payload 98개
- 시험지 메타데이터 5개
- 시험지 슬롯 250개

검증 후에는 프로세스 메모리의 불변 스냅샷에서 깊은 복사본을 반환한다. 따라서 학생의 시작·답안 검증·최종 채점 과정에서 정적 SQLite 연결을 반복 생성하지 않는다.

운영 DB 쓰기는 사용자 상태에 필요한 최소 범위로 제한한다.

- 시작 시 세션 1건 저장
- 문항 제출 시 답안 1건 upsert
- 최종 제출 시 사용자·태그 레이팅을 단일 트랜잭션으로 반영

## 10. 운영 DB 전환

기존 `quests.db`에서 더 이상 사용하지 않는 다음 테이블을 제거했다.

```text
level_test_template
level_test_template_item
```

다음 운영 데이터는 보존했다.

```text
level_test_session
level_test_answer
level_test_result
user_rating
user_tag_stats
```

전환 직전 운영 DB는 다음 파일로 백업했다.

```text
omj/quests.db.bak_before_level-test-static-v1
```

마이그레이션 스크립트를 다시 실행했을 때 제거 대상 0개, 보존 데이터 동일, 무결성 `ok`로 확인되어 멱등성도 검증했다.

## 14. 배포 및 변경 절차

문항을 추가하거나 교체할 때는 운영 중인 정적 DB를 직접 수정하지 않는다.

1. `seed_level_test_static_db.py`의 저작 문항 또는 후보 분류를 수정한다.
2. 빌드 스크립트를 실행해 임시 DB 전체를 생성한다.
3. 무결성·외래키·분포·JSON 검증이 모두 통과하면 파일을 원자 교체한다.
4. 회귀 테스트와 레이팅 시뮬레이션을 수행한다.
5. 새 정적 DB와 코드를 함께 배포하고 서버를 재시작한다.

정적 DB 파일만 교체하고 서버를 재시작하지 않으면 기존 프로세스의 메모리 스냅샷이 유지되므로, DB 변경 배포에는 서버 재시작이 필수다.

## 15. 잔여 참고사항

운영 `quests.db`에는 이번 작업 이전부터 존재한 다음 외래키 오류가 한 건 있다.

```text
exam_item rowid 482 -> exam
```

이 오류는 레벨테스트와 무관하며, 전환 전 백업에도 동일하게 존재한다. 시험 이력 보존 범위를 침범하지 않기 위해 이번 작업에서는 삭제하지 않았다. 정적 레벨테스트 DB의 외래키 오류는 0건이다.

## 16. 결론

레벨테스트는 이제 직접 검수된 고정 문제만 사용하며 일반 문제은행·실시간 생성기·클라이언트 입력 태그에 의존하지 않는다. 문제 원본은 별도 읽기 전용 DB에 물리적으로 격리됐고, 서버 시작 시 전체 스냅샷을 검증·캐싱하므로 높은 동시접속 환경에서도 정적 문제 조회로 인한 반복 DB 부하가 발생하지 않는다.

레이팅 시뮬레이션, API 위변조 검증, 운영 DB 분리, 결정적 재빌드와 회귀 테스트를 모두 통과했으므로 현재 상태는 운영 배포 가능한 정적 레벨테스트 구성으로 판단한다.
