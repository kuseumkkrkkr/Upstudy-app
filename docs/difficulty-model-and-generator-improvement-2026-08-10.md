# Upstudy 난이도 모델과 문제 생성 알고리즘 개선안

> 작성일: 2026-08-10
> 범위: 평가원 수학 690문항 분석과 현재 Upstudy 생성 경로를 대조한 설계안이다. 이 문서는 구현 제안이며, 생성 API나 배포 동작을 변경하지 않는다.

## 결론

난이도는 하나의 숫자로 결정하면 안 된다. Upstudy에서는 아래 세 값을 분리해 관리하는 것이 맞다.

| 구분 | 뜻 | 지금 바로 가능한가 | 용도 |
| --- | --- | --- | --- |
| 구조 난이도 | 태그 수, 풀이 흐름, 분기, 전략 등 생성 설계의 복잡도 | 가능 | 생성 계약과 품질 검증 |
| 평가원식 배점 적합성 | 생성 문항이 평가원 2·3·4점 문항의 구조와 얼마나 닮았는가 | 가능 | 후보 재선택과 검수 우선순위 |
| 학생 체감 난이도 | 특정 능력대 학생의 정답 확률·풀이 시간·변별도 | 아직 불가 | 개인화, OVR, 출제 난이도 보정 |

임베딩 모델로 두 번째 모델은 만들 수 있다. 그러나 현재 검증 결과상 임베딩만으로는 구조 변수보다 약하며, 세 번째인 실제 학생 난이도를 배점 데이터만으로 만들 수는 없다. 학생의 첫 풀이 응답과 시간을 받아 IRT로 보정해야 한다.

가장 중요한 생성기 개선은 “문항을 만든 뒤 구조와 의미를 측정해 목표 구간에 맞는 후보만 고르는 것”이다. 문장을 길게 하거나 숫자를 키워 점수를 올리는 방식은 금지한다.

## 1. 분석 근거와 해석 범위

분석 대상은 2022~2026학년도 평가원 6월·9월·수능 수학 15회차, 중복 제거 690문항이다. 공식 배점 분포는 2점 75문항, 3점 330문항, 4점 285문항이다.

회차 단위 GroupKFold 5분할로 검증했다. 문항번호, 페이지, 열 위치, 정답, 회차, 과목, 응답 형식은 입력에서 제외했다. 따라서 무작위 문항 분할보다 실제 새 회차 일반화에 가까운 결과다.

| 모델 | 입력 | Balanced accuracy | Macro-F1 | 해석 |
| --- | --- | ---: | ---: | --- |
| Dummy | 최빈 배점 | 0.333 | 0.216 | 비교 기준 |
| 구조 모델 | 49개 구조·수식·레이아웃 변수 | **0.859** | 0.832 | 현재 최선의 배점 스타일 기준선 |
| Granite | 한국어 문항 임베딩 384차원 | 0.745 | 0.700 | 의미 신호는 있으나 단독으로 약함 |
| MAMUT | 수식 표현 768차원 | 0.739 | 0.702 | 탐색용 수식 표현 |
| Hybrid | 구조 + 두 임베딩 | 0.856 | **0.837** | F1만 소폭 상승, 정확도 개선 근거 없음 |

이 수치는 “평가원이 부여한 2·3·4점 배점”을 분류한 결과다. 정답률, 풀이시간, 학생의 심리측정 난이도를 뜻하지 않는다.

특히 임베딩 군집과 배점의 일치는 매우 낮았다. Granite ARI는 0.004, MAMUT ARI는 0.019였다. 2·3·4점이 의미 공간에서 자연스럽게 세 집단으로 나뉜다는 근거는 없다.

### 배점과 함께 증가한 관측값

| 관측 변수 | 2점 중앙값 | 3점 중앙값 | 4점 중앙값 | 올바른 해석 |
| --- | ---: | ---: | ---: | --- |
| 큰 구성 요소 수 | 54 | 87.5 | 206 | 문항 정보량·수식/그림 밀도 |
| 연결 구성 요소 수 | 56 | 95.5 | 222 | 수식·문장·도형의 구성 복잡도 |
| 한글 문자 수 | 9 | 23 | 68 | 조건과 상황 설명량 |
| 수식 구간 수 | 20 | 26 | 45 | 표현된 수식 구조의 수 |
| 서로 다른 라틴 변수 수 | 2 | 3 | 5 | 조작 대상 수 |
| 관계 기호 수 | 1 | 2 | 4 | 등식·부등식·관계의 밀도 |

위 값은 결과 점검에는 유용하지만 생성 목표로 직접 쓰면 안 된다. 예를 들어 문장을 늘리거나 줄바꿈을 많이 해도 학생에게 본질적으로 어려운 문제가 되지는 않는다. 렌더링 길이·면적은 이상치 탐지와 QA용으로만 쓴다.

## 2. 무엇을 기준으로 난이도를 결정해야 하는가

문항 난도는 다음 네 층의 증거를 합쳐 판단한다.

| 층 | 핵심 질문 | 생성 시 확보할 원본 | 모델에서의 역할 |
| --- | --- | --- | --- |
| 수학 구조 | 몇 개의 개념·조건·관계를 결합해야 하는가 | 개념 태그, 조건 그래프, 수식 AST, 변수/관계/분기 | 가장 중요한 통제 변수 |
| 표현 전환 | 문장↔식, 그래프↔식, 도형↔좌표 중 무엇을 변환해야 하는가 | 도형 객체·관계, 그래프 스펙, 표/수식 구조 | 도형·그래프 문항 보완 |
| 풀이 부담 | 필요한 추론·경우 분류·역추론·대수 변형은 얼마나 되는가 | 풀이 플로우, 전략 노드, 검증 단계 | 구조 난도와 해설 품질 |
| 실제 반응 | 어떤 능력대가 얼마나 자주, 얼마나 오래 틀리는가 | 익명 첫 풀이 결과, 시간, 힌트, 재시도 | 체감 난도의 정답 레이블 |

단원명만으로 난이도를 판단하면 안 된다. 극한·미분·확률 모두 직접 적용형과 복합 추론형이 공존한다. 반대로 “그래프가 있다”, “조건이 많다”도 그 자체로 난도를 보장하지 않는다. 조건이 풀이에 실제로 필요한지, 서로 결합되는지, 어떤 표현 전환을 요구하는지가 중요하다.

### Upstudy가 보존해야 할 생성 원본

생성 문항은 PDF에서 다시 복원하지 말고, 생성 순간의 구조를 저장해야 한다.

- LaTeX 또는 MathML과 수식 AST
- 변수, 식, 부등식, 범위, 경우 분류의 관계 그래프
- 도형·그래프의 객체, 좌표, 교점, 보조선, 축·구간 스펙
- 각 풀이 단계의 목적, 사용 개념, 분기, 검산 조건
- 태그와 선행 개념 그래프
- 코드베이스 ID, 코드 해시, 시드, 생성 모델/프롬프트 버전

이 원본이 있어야 “분수선을 더 많이 그렸으니 어렵다” 같은 표면적 프록시가 아니라 실제 수학 구조를 측정할 수 있다.

## 3. 임베딩 모델로 난이도 결정 모델을 만들 수 있는가

### 답: 가능하지만 단독 결정기는 아니다

Granite는 한국어 문장 맥락, MAMUT는 수식 표현의 보조 신호로 유용하다. 현 분석에서도 두 임베딩 모두 Dummy보다 훨씬 높게 배점 스타일을 분류했다. 다만 구조 모델보다 약하고, Hybrid의 balanced accuracy는 오히려 0.859에서 0.856으로 소폭 낮아졌다.

따라서 권장 순서는 아래와 같다.

1. 수식 AST·조건 그래프·풀이 플로우를 우선 특징으로 사용한다.
2. 임베딩은 비슷한 문항 검색, 중복 방지, 경계 후보 재순위화에 사용한다.
3. 그래프·도형 문항에는 텍스트 임베딩 외에 도형 구조 또는 이미지 표현을 추가한다.
4. 출력은 단일 점수가 아니라 “각 구간의 확률 + 불확실성 + 근거”로 제공한다.

현재 분석에는 텍스트와 단순 수식 스트림은 같지만 그래프 그림이 다른 문항 쌍이 있었다. 텍스트 임베딩은 이 차이를 구분하지 못한다. 따라서 텍스트·수식 임베딩만으로 그래프 문제의 난도를 확정하면 안 된다.

MAMUT은 문장 임베딩 전용 head가 없는 mean-pooling 탐색 표현이므로, 현 상태에서는 단독 운영 모델이 아니라 실험용 보조 특징으로 한정한다.

### 권장 모델 출력

~~~text
official_score_style:
  probabilities: {2: 0.08, 3: 0.61, 4: 0.31}
  predicted_band: 3
  confidence: 0.61
  model_version: score-style-v0

student_difficulty:
  status: not_observed | estimated | calibrated
  predicted_p_correct_by_ability_band: ...
  predicted_time_seconds: ...
  uncertainty: ...
~~~

첫 줄은 현재 데이터로 만들 수 있다. 둘째 줄은 학생 반응이 쌓인 뒤에만 신뢰 가능한 값이 된다.

## 4. 학생 체감 난도는 IRT로 보정한다

평가원 배점은 학생 난도의 대체 라벨이 아니다. 학생 난도를 만들려면 문항 버전별 첫 풀이 데이터를 축적해야 한다.

~~~text
item_version_id
익명 사용자 ID
첫 풀이 여부와 재시도 횟수
정답 · 오답 · 미응답
풀이 시작·종료 시각
힌트 사용과 해설 열람 시점
학습 모드 · 시험 모드
코드베이스 ID · 코드 해시 · 시드 · 생성 프로필 버전
~~~

초기에는 Rasch 모형으로 시작하고, 표본이 충분하고 안정성을 확인한 뒤 2PL을 검토한다.

~~~math
P(정답 | 학생 능력 theta, 문항 난이도 b)
= sigmoid(a × (theta - b))
~~~

- b: 문항 난이도
- a: 변별도
- theta: 학생 능력

새 문항은 반응이 없으므로 구조·임베딩 모델이 사전 난도를 예측한다. 학생 풀이가 누적되면 IRT가 사후 난도와 변별도를 갱신한다. 시간은 정답률과 섞지 않고 별도 결과로 관리한다.

~~~mermaid
flowchart LR
    A[문항 원본: 태그·AST·도형·풀이 플로우] --> B[결정적 구조 특징]
    A --> C[한국어·수식·도형 임베딩]
    B --> D[사전 난도 모델]
    C --> D
    D --> E[예측 난도·신뢰구간]
    F[익명 학생 첫 풀이 로그] --> G[IRT 보정]
    E --> G
    G --> H[검증 난도·변별도·시간 분포]
    H --> I[문항은행과 생성기 보정]
~~~

초기 운영에서는 “예측 난도”와 “검증 난도”를 화면·API에서 구분한다. 독립 첫 풀이 표본이 충분하지 않은 문항을 확정 레벨이나 OVR 근거로 쓰지 않는다.

## 5. 현재 Upstudy 생성기의 상태

### OMJ main 경로

현재 OMJ는 이미 생성 구조를 계약으로 관리한다.

- **omj/generater/codebase_runner.py** 의 estimate_difficulty는 태그 수 + 4×풀이 수 + 3×분기 조건 + 2×전략 수준이다.
- **omj/generater/fix_gen.py** 의 calculate_difficulty는 태그 수 + 4×실제 플로우 수 + 3×분기 레인 수 + 2×enter_huddle 합계다.
- **omj/generater/make.py** 는 태그·계약 난도에 맞는 코드베이스와 검증된 시드를 우선 고르고, 실행 결과를 검증한 뒤 fix_gen으로 저장한다.
- **omj/generater/problem_solve.py** 는 difficulty_tier와 difficulty_score를 구분해 학생용 계약을 마무리한다.
- **omj/server.py** 의 advanced_metrics는 trap, condition_density, algebra_steps, graph_depth, top_rate 등을 생성 지시로 전달한다.

이 구조 난도는 가치가 있다. 다만 그것은 “생성자가 설계한 복잡도”이며 “학생이 실제로 어려워하는 정도”는 아니다. 특히 top_rate는 현재 생성 지시값일 뿐 실제 사용자 정답률로 쓰면 안 된다.

~~~mermaid
flowchart LR
    A[요청: 태그·풀이 수·전략·분기] --> B[estimate_difficulty]
    B --> C[코드베이스·검증 시드 선택]
    C --> D[generate_problem(seed)]
    D --> E[validate_result]
    E --> F[fix_gen]
    F --> G[구조 난도 점수·tier 저장]
~~~

### Vercel 경로는 별도 확인이 필요하다

로컬에서 확인한 Vercel checkout의 **api/index.py** 는 /quests/generate와 /quests/generate/stream에서 결정적 일차방정식 생성기 _build_generated_questions를 직접 호출한다. 요청의 태그·풀이 수·전략·분기 조건은 난도 구조를 실제로 구성하지 않는다.

또한 이 로컬 checkout은 확인 시점에 origin/vercel보다 41커밋 뒤였다. 따라서 이 파일만으로 현재 운영 배포본을 단정할 수는 없다. 구현 전에 반드시 원격 vercel 브랜치, 실제 Vercel 배포 번들, /quests/generate 응답을 함께 확인해야 한다.

즉 OMJ만 개선해도 Vercel 사용자 경로에 반영되지 않을 수 있다. 난도 로직은 두 경로에 따로 복제하지 말고 하나의 버전 있는 공통 모듈 또는 공통 서비스 계약으로 맞춰야 한다.

## 6. 제안하는 생성 알고리즘

### 목표 난도 벡터

생성 요청은 단일 tier 대신 아래 목표를 가져야 한다.

| 필드 | 예시 | 쓰임 |
| --- | --- | --- |
| target_tier | 1~5 | 기존 풀이·분기 계약 |
| target_score_style | 2·3·4 또는 미지정 | 평가원식 형태 목표 |
| target_ability_band | OVR 구간 | 학생 반응 모델이 생긴 뒤 사용 |
| target_p_correct | 0.35~0.55 | 검증 난도 모델이 생긴 뒤 사용 |
| concept_tags | 함수, 미분 | 출제 범위 |
| required_relations | 조건 결합, 경우 분류 | 실제 수학 구조 |
| representation | 수식, 그래프, 도형, 표 | 표현 전환 요구 |
| advanced_metrics | trap, algebra_steps 등 | 생성 지시와 사후 점검 계약 |

기존 difficulty와 difficulty_score는 하위 호환성을 위해 유지한다. 새 필드는 difficulty_profile 또는 difficulty_evidence에 추가하고, 구조 점수는 구조 난도라는 이름으로 명확히 구분한다.

~~~mermaid
flowchart TD
    A[출제 청사진] --> B[목표 난도 벡터]
    B --> C[기존 코드베이스·검증 시드 후보]
    C --> D[후보 문항 생성]
    D --> E[수학 정합성·태그·풀이 계약 검사]
    E -->|실패| C
    E --> F[AST·조건·도형·풀이 특징 추출]
    F --> G[배점 적합성·사전 난도 추정]
    G --> H{목표 구간과 신뢰도 충족?}
    H -->|아니오| I[다음 시드·다른 코드베이스 선택]
    I --> C
    H -->|예| J[중복·정답 누설·표현 QA]
    J -->|실패| I
    J -->|통과| K[문항은행 저장]
    K --> L[학생 반응 수집]
    L --> M[IRT 보정]
    M --> B
~~~

후보를 재선택할 때는 새 LLM 코드를 즉시 다시 만들기보다, 이미 수학적으로 검증된 같은 코드베이스의 시드를 먼저 평가한다. 비용·지연을 줄이고 codebase_id와 seed 재현성도 보존할 수 있다.

### 난도를 올리고 내리는 올바른 방법

| 조정 축 | 올리는 방법 | 내리는 방법 |
| --- | --- | --- |
| 조건 복잡도 | 독립적이면서 꼭 필요한 조건을 결합 | 중복 조건 제거, 조건을 명시적으로 분리 |
| 관계 복잡도 | 함수·식·부등식·도형 관계를 연결 | 핵심 관계 하나로 축소 |
| 개념 전환 | 두 개념 사이의 연결을 요구 | 한 개념의 직접 적용으로 제한 |
| 풀이 경로 | 경우 분류, 역추론, 표현 전환 추가 | 정방향 단일 경로 제공 |
| 도형/그래프 | 의미 있는 객체 관계·좌표화 요구 | 그림은 유지하되 필요한 관계를 명시 |
| 계산 | 판단 뒤 필요한 계산 단계만 추가 | 판단 구조를 유지한 채 계산을 축소 |

다음은 금지한다.

- 문장 길이, 줄바꿈, 숫자 크기만 늘려 난도를 올리는 행위
- 필요하지 않은 조건·그래프·수식을 붙이는 행위
- 배점 분류기를 통과하기 위해 지면 면적이나 글자 수를 조작하는 행위
- 임베딩 유사도만으로 정답성·난도를 확정하는 행위

## 7. 코드 통합 순서

### 1단계: 모델 없이 계약과 증거를 정리

1. **omj/generater/difficulty_features.py** 를 추가한다. 입력은 생성 결과와 원본 AST/도형/풀이 플로우이며, 출력은 결정적인 구조 특징이다.
2. **fix_gen.py** 의 기존 점수는 제거하지 않고 structural_difficulty_score라는 의미로 함께 저장한다.
3. **make.py** 와 **problem_solve.py** 에 generation_profile, codebase_id, code_hash, seed, 추출 특징 버전을 보존한다.
4. **server.py** 의 advanced_metrics를 생성 지시와 사후 검증 가능한 계약으로 분리한다. top_rate는 observed_top_rate가 생기기 전까지 요청 가설로만 보관한다.

### 2단계: 평가원식 배점 적합성 모델을 그림자 모드로 운영

1. 평가원 690문항과 Upstudy 검수 문항으로 구조 기반 기준 모델을 학습한다.
2. 생성 결과마다 2·3·4점 확률, confidence, model_version만 계산하고 아직 사용자 난도나 출제 결과를 바꾸지 않는다.
3. 회차 홀드아웃뿐 아니라 코드베이스·템플릿 홀드아웃으로도 검증한다.
4. 예측이 불확실하거나 목표 구간에서 먼 후보만 검수 큐로 보낸다.

임베딩은 첫 출시에서 필수가 아니다. 경계 후보의 재순위화·유사 문항 중복 방지로 시작하고, 구조 모델보다 일관되게 개선되는 검증을 통과할 때만 포함한다.

### 3단계: 검증 시드 후보의 선택기에 연결

- **OMJ**: make.py에서 validate_result를 통과한 뒤, fix_gen 전후의 확정 문항 구조로 점수를 계산한다. 목표와 맞지 않으면 같은 코드베이스의 다음 검증 시드를 우선 사용한다.
- **학생용 생성**: problem_solve.py에서 fix_gen 직후, finalize_student_quest 전에 같은 검사를 적용한다. 기존 difficulty_tier, 헤더·data·solves API 계약은 보존한다.
- **Vercel**: api/index.py의 단순 생성기를 그대로 점수화하는 것은 충분하지 않다. 실제 태그·풀이·분기 구조를 만드는 공통 생성 경로로 연결한 뒤 같은 scorer를 적용한다.

Vercel 함수의 최대 실행 시간은 30초다. 따라서 요청 경로에서 대형 임베딩 모델을 매번 로드하거나 외부 LLM을 동기 호출하지 않는다. 구조 scorer와 사전 계산된 시드 점수를 캐시하고, 임베딩은 비동기 검수·발행 작업에서 계산한다.

### 4단계: 실제 반응 기반 모델

1. 익명화된 첫 풀이 이벤트를 저장하고 중복·재시도·힌트·시험 모드를 분리한다.
2. 새 문항은 사전 난도, 충분히 관측된 문항은 IRT 보정 난도로 표기한다.
3. 정답 확률, 풀이 시간, 변별도를 개별 결과로 유지한다.
4. OVR은 검증 난도 문항의 반응을 우선 사용하며, 예측 난도 문항에는 낮은 가중치 또는 탐색용 가중치만 준다.

## 9. 검증·보안·운영 게이트

| 게이트 | 통과 조건 |
| --- | --- |
| API 호환성 | 기존 header, data, solves, difficulty_tier 응답 계약과 스트리밍 형식 유지 |
| 재현성 | 같은 code_hash와 seed에서 동일한 특징·예측·문항을 반환 |
| 생성 정합성 | 태그, 풀이 수, 분기, 정답, 해설 계약을 기존보다 약화하지 않음 |
| 모델 검증 | 회차·템플릿 홀드아웃, 확률 보정, 도형/그래프/단원별 편향 점검 |
| 배포 안전성 | 그림자 모드 → 내부 검수 → 소량 발행 → 전체 발행 순서 |
| 성능 | 예측 캐시 키를 model_version:code_hash:seed로 고정하고, 사용자 요청에서 대형 모델을 로드하지 않음 |
| 개인정보 | 사용자 ID는 가명화하고, 원문 풀이·필기 이미지는 난도 모델 학습에 무단 투입하지 않음 |
| 불확실성 | confidence가 낮은 문항은 자동 발행·OVR 반영 대신 검수 큐로 이동 |

기존에 유지해야 할 회귀 테스트는 아래다.

- omj/tests/test_difficulty_distribution.py
- omj/tests/test_problem_solve_single_count.py
- omj/tests/test_variant_generation_bottleneck.py
- omj/tests/test_postgres_problem_store.py
- Vercel의 /quests/generate 및 /quests/generate/stream 응답 스냅샷 테스트

새 테스트는 목표 tier 통과/거절, 동일 시드 결정성, 다음 시드 재선택, 특징 누설 방지, scorer 미가용 시 안전한 기존 경로 fallback을 포함한다.

## 10. 실행 우선순위

1. **배포 경로 확정**: GitHub origin/vercel, Vercel 배포본, 실제 /quests/generate 결과를 대조해 OMJ와 Vercel 중 어느 코드가 사용자 요청을 처리하는지 확정한다.
2. **공통 구조 특징 계약**: AST·도형·풀이 플로우를 저장하고 기존 구조 난도와 새 evidence를 분리한다.
3. **그림자 scorer**: 구조 기반 배점 적합성 모델만 붙여 생성 결과를 바꾸지 않고 검증한다.
4. **시드 재선택**: 검증된 후보 중 목표와 맞는 문항을 고른다.
5. **IRT 보정**: 실제 첫 풀이 데이터가 축적된 뒤에만 학생 체감 난도·OVR에 반영한다.

이 순서라면 현재 생성 계약과 사용자 경험을 깨지 않으면서, 단순한 구조 점수에서 실제 학습자 중심 난도 모델로 이동할 수 있다.
